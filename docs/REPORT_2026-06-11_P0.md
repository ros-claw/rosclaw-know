## 5. 关键决策记录

### 5.1 为什么 routing_panel.yaml 用 verify_frontier_eng symptom 作为 query

doc §6 强调"硬门槛", 但要"硬"就必须用 paired_ab 实际会发的同一个查询字符串去 probe。否则我们 verify 的是 routing 在 X 查询下正确, paired_ab 跑的是 Y 查询, X≠Y → 假阳性。所以 routing_panel.yaml 的 18 个 query 全部 verbatim 复制自 `scripts/verify_frontier_eng.py` BENCHMARK_SUITE 的 symptom 字段。

之前 `build_routing_canary.py` 的 canary 是用 curated `standard_name + matched_keywords` 合成的"reasonable error log", 那是给 HOW 自己 reload 后 self-probe 用的(防止 ANN drift), 跟 paired_ab 的实际 routing query 不是同一个 schema。**两个 canary 不冲突, 服务不同目的**。

### 5.2 为什么 invalid 样本 status 分三种

```python
invalid_provider_failure  ← agent 端返回 "[agent call failed:...]" 等 marker
invalid_judge_failure     ← judge 自己返回空 / 主备 fallback 都失败
invalid_judge_parse       ← judge 返回内容但 SCORE_RX 解析不出
```

三种都属于 `pair_status="invalid"`, 都不进 mean Δ。但分类保留, 便于事后定位是 agent 端坏了还是 judge 端坏了。iter4_p9 当前 paired_ab seed_1 的 T_005 control 35-byte 就是 `invalid_provider_failure`(agent 端 reasoning-budget 耗尽), 不是 judge 问题。

### 5.3 为什么 GLM 是 fallback 而不是主 provider

GLM-4.7-Flash 上下文窗口和 reasoning 深度都比 step-3.7-flash 浅, 单独跑 18-task 面板的"绝对分数"会失真; 但作为 fallback 只在主 judge 完全失败时启用, 拿到的也是相对"是否完成评分"的兜底, 不是绝对分数比较。把它当兜底, 不当对手。

### 5.4 为什么 publish_to_how topic_coverage 是 BLOCKING 而不是 WARNING

iter4_p3 → iter4_p4 之间整整一周时间因为这个 bug 浪费 — KNOW 只加了 topic_group, HOW 的 `_build_group_to_fingerprint_text` 静默 drop, 14 个 curated 等于没起作用, 直到 iter4_p4 加 topic_tag 才修好。任何让"silent dead code"再次发生的成本都远超 BLOCKING 带来的不便。
