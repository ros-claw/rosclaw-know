## 1. 项目目标(为什么有这套东西)

ROSClaw-KNOW 是离线侧。负责把"具身智能工程师常见症状 → 通用补救方案"的知识沉淀成一个可被 LLM agent 在线检索的 curated 库。架构上:

```
   curated_patterns.py (源代码,15 个 CuratedPattern)
       │
       ▼
   curated_publisher.publish_curated_assets()
       │
       ▼
   data/assets/bridge_index.json (HOW 加载的运行时索引)
       │ POST /admin/reload
       ▼
   HOW (FastAPI / SeekDB router) — 处理 /prompt/build 请求
       │ ↑↓ X-API-Key
   verify_frontier_eng.py (paired_ab harness)
       │  control = LLM 直答; treatment = HOW 注入 snippet 后再答
       ▼
   judge_frontier_eng.py (LLM 当裁判,1-10 打分)
       │
       ▼
   data/benchmarks/paired_ab/<label>/seed_X/summary.json + seed_X.judge.log
```

**用户唯一原则**(项目宪法,已写入 memory):
> "我就一个原则,希望 know-how 是通用的"

也就是:**禁止针对某一个具体任务做 per-task hack**。所有改动必须是结构性规则、通用 vocab、或 retrieval mechanism 的调整。

### 主因:302.ai step-3.7-flash 免费层不稳定

切到 step-3.7-flash(用户 2026-06-10 directive:禁用付费 deepseek-chat)后,在 5 次连发 burst 测试中:

```
call 1: HTTP 429 err_code=-10003 "Parameter error"  (~1s)
call 2: HTTP 200 success                            (14s)
call 3: HTTP 429 err_code=-10003 "Parameter error"  (~1s)
call 4: HTTP 429 err_code=-10003 "Parameter error"  (~2s)
call 5: HTTP 200 success                            (17s)
```

**这不是真的 rate limit(没有 Retry-After header),是 302.ai 免费层 load balancer 拒绝**。同一个 well-formed payload 一会儿 200 一会儿 429。错误 body 永远是 `err_code: -10003 Parameter error` —— 但参数实际上没错(其他时候同一个 body 200 OK)。

**我已经做的补救**:
- `verify_frontier_eng.py:_call_agent`: 双层 retry —— 内层 6 次 exponential backoff(2/4/8/16/32/64s)针对 429/5xx/-10003;外层 1 次针对 reasoning model 空内容(8000→16000 max_tokens)
- `judge_frontier_eng.py:_chat_seeded`: 同 retry 模式的 aiohttp 异步版本

**但 judge log 显示**:即使 6 次 retry,有些 task 的 judge call 还是穿透到最终 None。这意味着 302.ai 免费层在繁忙时段(我猜跨时区的高峰)失败率可能远高于我测试时的 50%。

## 6. 现在最棘手的 2 个问题(讨论焦点)

### 问题 A:验证渠道脆弱 — step-3.7-flash 在 302.ai 上有 ~30-50% 单次失败率

**症状**: HTTP 429 with `err_code: -10003 "Parameter error"`(并非真 rate-limit),或 HTTP 200 with `finish_reason=length, content=""`(reasoning model 在 8000 tokens 里没产出内容)。

**影响**: 单 seed 跑 ~93 分钟,且有 ~10-30% 的 task 因为 control 或 judge 一侧空数据而拿不到可信 Δ。10-seed 跑批需要 15+ 小时,而且最后聚合时数据洞很多。

**讨论选项**:
- a. **接受**:跑完 10 seeds,过滤掉异常,看主因(seed_1 的 T_002/T_005/T_008/T_W_002 是真信号,T_001 是 control-side 数据洞)
- b. **换 provider**:除了 302.ai,有没有其它能跑 step-3.7-flash 的免费/付费通道?(deepseek 官方 v4-flash?Anthropic Haiku 4.5?)
- c. **缓存 control 复用**:control 是 baseline LLM 答(不依赖 HOW),iter4_p9 跟 iter4_p8 跑的是 **same** task / same model / same seed。能不能复用 iter4_p8 的 control,只跑 iter4_p9 的 treatment?这一招省 50% LLM 调用,但要求 LLM 在 iter4_p8(deepseek-chat)和 iter4_p9(step-3.7-flash)同 seed 同温度下产物可比 —— 跨模型可比性是个独立 question。
- d. **不依赖 judge 跑分,改用 retrieval-only 指标**:iter4_p9 ship 已经 live-probe 确认 T_001 routing flipped。如果只看 retrieval 正确率(inject 是否到了 canonical curated),就不需要跑 LLM 跑分。但这放弃了 "fix actually improves the LLM answer" 这个真目标。

我的初步倾向:**a + d 双轨**。让现在这个 paired_ab 跑完(免费的就让它跑),同时把 retrieval 正确率作为 ship 的硬验收线、把 LLM 跑分作为软指标。

### 问题 B:iter4 弧的 ceiling — 还能往哪走

**ship 进度**:
- 路由 / 结构层完成:14/14 curated 全部带 topic_group + topic_tag,iter4_p8 PANEL +0.93 在 deepseek-chat 上是整弧最高。
- 内容工程首例:iter4_p9 NEW cluster 在 live probe 上确认 T_001 routing 修复。
- 5 个 wild cold spots 中 4 个已 LLM-saturated(裸 LLM 已经能答对到 9.7+/10),只剩 T_W_002 有非平凡 headroom(C̄=9.0)。
- 5 个 home cold spots:T_001(iter4_p9 内容工程修),T_005(iter4_p4 routing 修),T_008(iter4_p8 surprise inject 修)。

**剩下能动的地方**:
1. **HOW 侧机制调整**:preference floor 0.60 偏紧 —— anti_windup_pid sim 0.5583 差一点没被 swap-in;能不能动态 floor?(不通用,可能反例)
2. **n=30 方法论收紧**:iter4_p1 n=10 +0.47 → n=30 +0.27,~40% 的 n=10 信号是 control-side 噪声拉高的。所有"新高"的弧上结论,在 n=30 下大概率退 30-50%。但 n=30 跑批在 302.ai step-3.7-flash 下需要 ~45 小时。
3. **认知:大部分 iter4_p3+ 的"弧上新高"是结构补全的 one-time gain**,不是可重复的迭代规律。如果再要 +Δ,得回到 wild distribution(新症状,bridge 还没覆盖的),或者放弃单 task lift 转去刷 retrieval coverage 指标。

我的初步看法:**iter4 弧已经接近收益边际**。再往下不该是"刷 PANEL Δ",该是:
- 把 ship 标准从 "PANEL Δ > 0" 改成 "retrieval injects 到 canonical curated" + "live-probe 无 collateral"
- 把 LLM 跑分降级为 "信心证据" 而不是 "硬验收线"
- 内容工程(像 iter4_p9 这样)只在 retrieval probe 抓到真错误(routing 走 wrong-domain synth)时才做,且必须有 4-6 个 task-distinctive tokens 把 collateral 推到 floor 以下
